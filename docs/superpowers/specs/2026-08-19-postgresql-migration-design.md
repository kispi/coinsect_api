# MySQL → PostgreSQL 마이그레이션 설계

작성일: 2026-08-19

## 목표

운영 중인 `coinsect` 데이터베이스를 MySQL 8.0.46에서 PostgreSQL 16.14로 옮긴다. 둘 다
`webserver.coinsect.io` 단일 EC2 인스턴스에 있고, 이관이 끝나면 MySQL을 내려 메모리와 CPU를
회수하는 것이 최종 목적이다.

동시에 처리할 것이 두 가지 더 있다.

1. **SQL Injection 차단.** 문자열 보간으로 SQL을 만드는 지점을 전부 파라미터 바인딩으로
   바꾼다. 이번 범위는 SQLi 한정이다. 인증, 비밀번호 해싱, 자격증명 평문 보관 같은 다른
   보안 문제는 별개 작업으로 다룬다.
2. **스키마 스냅샷 재설정.** 기존 마이그레이션 31개를 버리고, 현재 운영 DB 상태를 그대로
   담은 단일 SQL 파일 하나를 새 기준선으로 삼는다.

## 범위 밖

- 인증/인가 로직 변경, 비밀번호 해싱 방식, `ormconfig.ts`의 평문 자격증명
- TypeORM을 다른 ORM으로 교체하는 것 (드라이버만 바꾼다)
- 성능 튜닝. 단, 이관 과정에서 명백히 중복인 인덱스는 제거한다
- 기존 데이터의 정합성 교정 (아래 "알려진 데이터 특성" 참고)

## 현재 상태

### 코드베이스

Fastify 5 + TypeORM 0.3.31 + mysql2. 엔티티 20개, 컨트롤러 20개. `SnakeNamingStrategy`로
모든 식별자가 snake_case다. `core/orm.ts`의 `querySetter`와 `core/controller.ts`의 `useCRUD`가
대부분의 조회/CRUD를 공통 처리한다.

### 데이터베이스

전체 약 230MB / 21개 테이블.

| 테이블 | 행 수 | 크기 |
|---|---:|---:|
| `messages_202605` | 852,544 | 155.2MB |
| `whale_alerts` | 80,492 | 71.6MB |
| `posts` | 1,221 | 6.6MB |
| `reactions` | 6,446 | 1.9MB |
| `messages` | 1,929 | 0.5MB |
| `replies` | 1,320 | 0.3MB |
| 나머지 15개 | 각 500 미만 | 합계 0.5MB 미만 |

PostgreSQL 쪽에는 아직 `coinsect` 롤도 `coinsect` 데이터베이스도 없다. 같은 인스턴스에
`gukto`, `calendar`, `everymaple`, `calendar_dev`가 이미 돌고 있다.

### 알려진 데이터 특성

**`messages_202605`는 살아있는 아카이브다.** 2026-05-20에 `messages`를 이 이름으로 rename하고
새 `messages`를 만든 흔적이다. 두 테이블의 id 범위가 1부터 겹친다 (`messages` 1~1944,
`messages_202605` 1~878422). `reactions.message_id`의 FK는 **`messages_202605`를 가리킨다.**
message 반응 1,806건 중 1,760건이 아카이브 쪽 행을 참조한다. 코드에서 이 테이블을 읽는 곳은
없지만 FK 대상이므로 구조를 1:1로 그대로 옮긴다.

**엔티티와 DB가 드리프트되어 있다.** `migrations` 테이블에는 30행이 있으나 파일은 31개이고
AUTO_INCREMENT는 33이다. 따라서 스키마 기준선은 엔티티가 아니라 **라이브 DB에서 뜬 DDL**로
잡는다.

**`whale_alerts`에는 타임스탬프 컬럼이 없다.** PK가 `hash`(varchar)이고 `id`도
`created_at`/`updated_at`도 없다. `persons_images` 조인 테이블도 마찬가지다.

## 설계

### 1. 산출물

```
schema/001_baseline.sql     현재 상태의 PostgreSQL DDL 스냅샷
tools/migrate/config.ts     테이블 목록 + 타입 변환 규칙
tools/migrate/copy.ts       전체 이관 / 델타 동기화 (같은 코드, 모드만 다름)
tools/migrate/verify.ts     행 수 + 샘플 대조
migrations/                 삭제 (파일 31개 + DB의 migrations 테이블)
```

### 2. 스키마 기준선

`mysqldump --no-data`로 뜬 라이브 DDL을 손으로 PostgreSQL DDL로 옮긴다. 사람이 읽고 검토할 수
있는 한 장짜리 파일이어야 하고, 복구는 `psql -f schema/001_baseline.sql` 한 줄이면 된다.
이후 스키마 변경은 `002_*.sql`, `003_*.sql`로 붙인다.

#### 타입 매핑

| MySQL | PostgreSQL | 비고 |
|---|---|---|
| `int AUTO_INCREMENT` | `integer GENERATED BY DEFAULT AS IDENTITY` | `BY DEFAULT`여야 이관 때 id 명시 삽입이 된다 |
| `datetime(6)`, `datetime` | `timestamptz` | 아래 "타임존" 참고 |
| `decimal(36,18)`, `decimal(20,2)` | `numeric(36,18)`, `numeric(20,2)` | |
| `tinyint NOT NULL DEFAULT '0'` | `boolean NOT NULL DEFAULT false` | `notifications.active` 하나뿐 |
| `varchar(255)`, `text`, `int` | 동일 | |
| `ON UPDATE CURRENT_TIMESTAMP(6)` | `BEFORE UPDATE` 트리거 | PostgreSQL에 대응 문법이 없다 |

#### 타임존

이 마이그레이션에서 가장 조용히 망가지기 쉬운 지점이다.

현재 `ormconfig.ts`에 `timezone: 'Z'`가 있어 mysql2가 DATETIME을 UTC로 해석한다. PostgreSQL에서
`timestamp without time zone`을 쓰면 node-postgres가 그 값을 **Node 프로세스의 로컬 시각**으로
파싱하므로, 전 시간 데이터가 서버 오프셋만큼 통째로 밀린다. 에러 없이 값만 틀어지기 때문에
발견이 늦다.

따라서:

- 모든 시각 컬럼은 `timestamptz`로 만든다.
- 세션 타임존을 UTC로 고정한다 (`extra: { options: '-c timezone=UTC' }`).
- 이관 스크립트는 MySQL을 `dateStrings: true`로 읽어 문자열 그대로 받고, `Z`를 붙여 넣는다.
  드라이버의 타임존 해석에 의존하지 않는다.

#### `updated_at` 트리거

MySQL의 `ON UPDATE CURRENT_TIMESTAMP(6)`을 대체할 트리거를 모든 `updated_at` 보유 테이블에
건다. TypeORM의 `@UpdateDateColumn`은 `save()` 경로에서만 확실히 동작하고 QueryBuilder를 통한
raw UPDATE에서는 보장되지 않는데, 델타 동기화가 `updated_at`을 기준으로 삼기 때문에 DB 레벨
보장이 필요하다.

```sql
CREATE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END;
$$ LANGUAGE plpgsql;
```

#### 인덱스 및 제약조건 정리

- `whale_alerts`의 `idx_amount_timestamp_owner`와 `idx_whale_main`은 컬럼 구성이 완전히
  동일하다. 하나만 남긴다.
- `whale_alerts`의 `IDX_7c748a8328297bc5b25d652109`는 PK(`hash`)와 중복인 unique 인덱스다.
  제거한다.
- 제약조건 이름은 TypeORM이 생성한 해시(`FK_9691367d446cd8b18f462c191b3`) 대신 읽히는 이름
  (`fk_auth_tokens_user`)으로 바꾼다. TypeORM은 런타임에 제약 이름을 참조하지 않으므로 안전하다.
- `migrations` 테이블은 기준선에 포함하지 않는다.

### 3. 데이터 이관

서버 위에서 SSH로 실행한다. 두 DB가 같은 인스턴스에 있으므로 localhost↔localhost로 흐르고,
230MB가 인터넷을 왕복하지 않으며 자격증명도 로컬 네트워크를 벗어나지 않는다. 서버 가용 메모리가
1GB뿐이라 배치는 1000행 단위로 끊는다.

#### 델타 전략

테이블별로 자동 선택한다. 테이블 목록을 손으로 관리하지 않아도 되도록 컬럼 존재 여부로 판정한다.

- **`updated_at`이 있는 테이블** — `WHERE updated_at >= :since`로 읽어
  `ON CONFLICT (id) DO UPDATE SET ...`. INSERT와 UPDATE(소프트삭제 포함)가 한 번에 처리된다.
- **`updated_at`이 없는 테이블** (`whale_alerts`, `persons_images`) — 전체를 다시 훑어
  `ON CONFLICT DO NOTHING`. 8만 행과 18행이라 부담이 없다.

이관 직후 각 identity 컬럼에 `setval`로 `MAX(id)`를 반영한다. 누락하면 첫 INSERT부터 PK 충돌이
난다.

**한계:** 하드 삭제된 행은 델타로 잡히지 않는다. 이 코드베이스는 사용자 콘텐츠를 전부
`softDelete`로 처리하므로 실질 영향은 없다.

### 4. 코드 변경

#### 드라이버

- `database.ts` — `type: 'mysql'` → `'postgres'`, `connectorPackage` 제거
- `ormconfig.ts` / `ormconfig.sample.ts` — 포트 5432, 호스트 `webserver.coinsect.io`,
  사용자 `coinsect`. `charset`(PostgreSQL에서 무의미)과 `timezone`(mysql 전용 옵션) 제거,
  `extra.options`로 세션 타임존 지정. `migrations` 글롭 제거
- `package.json` — `mysql2` → `pg`

호스트는 기존 `api.coinsect.io`에서 `webserver.coinsect.io`로 통일한다. 동일 IP를 가리키지만
다른 프로젝트들이 후자를 쓰고 있다.

#### SQL Injection 차단

`?where=`는 구조화 DSL로 교체한다. 현재는 쿼리스트링이 WHERE 절에 그대로 붙고, 이 경로가
`/boards`, `/notifications`, `/wallets`, `/posts`, `/price_predictions`, `/whale_alerts` 등
**인증 없는 공개 엔드포인트**에서 쓰인다.

```
Before: ?where=amount_usd >= 3000000        (임의 SQL)
After:  ?where=amountUsd:gte:3000000        (field:op:value)
```

허용 연산자는 `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `like`, `in`, `isnull`. 필드는 엔티티
메타데이터에 실재하는 컬럼만 통과시키고, 값은 파라미터로 바인딩한다. `sort`와 `join`도 같은
방식으로 화이트리스트를 건다. `limit`/`offset`은 숫자로 캐스팅하고 상한을 건다.

`whale_alerts` 목록을 내부에서 호출하는 `services/dashboard.ts`도 새 문법으로 맞춘다.

나머지 보간 지점:

| 위치 | 문제 |
|---|---|
| `core/orm.ts:20` | `?where=` 임의 SQL — 공개 엔드포인트, 인증 없음 |
| `core/controller.ts:31,38` | `id = ${params.id}` — 전 admin CRUD의 detail/delete |
| `core/controller.ts:82` | `IN (:id)` 배열 바인딩 — PostgreSQL에서 깨진다. `IN (:...ids)`로 |
| `entities/message.ts:9` | `IN (${ids.join(',')})` |
| `admin_controller.ts:53` | `ip = "${body.ip}"` — 큰따옴표는 PostgreSQL에서 식별자 |
| `admin_controller.ts:101` | `Post.id = ${params.id}` |
| `auth_controller.ts:38` | `email = '${email}'` — 로그인 경로 |
| `reaction_controller.ts:11,41,70,99` | `message_id = ${body.messageId}`, `id = ${...}` |
| `post_controller.ts:142` | `sharing_key = '${params.sharingKey}'` |
| `price_prediction_controller.ts:74` | `sharing_key = '${params.sharingKey}'` |
| `services/post.ts:40-43` | `LIKE "%${keyword}%"` — 검색어 그대로 |
| `services/price_prediction.ts:33-34` | `LIKE "%${keyword}%"` |
| `chat/controllers.ts:292` | `Message.id < ${cursor}` |
| `dashboard_controller.ts` | `${tablename}` 보간, `start`/`end` 날짜 문자열 |
| `notification_controller.ts:8` | `active = 1` — PostgreSQL에서 boolean 타입 에러 |

`dashboard_controller.ts`의 `tablename`은 이미 코드 내부 상수 배열에서만 오지만, 화이트리스트
검증을 명시적으로 넣어 향후 유입 경로가 생겨도 막히게 한다. `start`/`end`는 파라미터로 넘긴다.

### 5. 컷오버

1. **리허설** — PostgreSQL에 `coinsect` 롤/DB 생성 → 기준선 적용 → 전체 이관 → verify.
   서비스는 계속 MySQL로 동작한다.
2. **코드 작업** — 드라이버 교체 + SQLi 차단 + DSL. 리허설 DB를 상대로 검증한다.
3. **컷오버** — API 정지 → 델타 실행 → `setval` → `EC2_ORMCONFIG` 시크릿 교체 후 배포 →
   기동 → smoke test.
4. **롤백** — 시크릿만 되돌려 재배포한다. MySQL은 손대지 않은 채 살아있다.
5. **정리** — 안정화 확인 후 MySQL 중지.

### 6. 검증

- 테이블별 행 수 대조 (MySQL vs PostgreSQL)
- 각 테이블 `MIN(id)`, `MAX(id)`, `MAX(updated_at)` 대조
- 시각 컬럼 샘플 대조 — 타임존이 밀리지 않았는지 확인하는 것이 핵심이다
- `numeric` 정밀도 샘플 대조 (`decimal(36,18)` 컬럼들)
- `notifications.active`의 boolean 변환 결과 대조
- TypeORM 부팅 + 주요 엔드포인트 smoke test
- `?where=` DSL의 거부 케이스 테스트 (임의 SQL이 400으로 막히는지)

## 리스크

| 리스크 | 대응 |
|---|---|
| 타임존 오프셋으로 전 시각 데이터가 밀림 | `timestamptz` + `dateStrings` 읽기 + 샘플 대조 검증 |
| 시퀀스 미설정으로 기동 직후 PK 충돌 | 이관 스크립트에 `setval` 포함, verify에서 확인 |
| `?where=` 문법 변경으로 프론트 기능 유실 | 프론트가 쓰는 조건을 먼저 조사해 DSL로 표현 가능한지 확인 |
| 서버 메모리 부족 (가용 1GB) | 1000행 배치, 스트리밍 읽기 |
| 델타 구간의 하드 삭제 유실 | 소프트삭제만 쓰므로 실질 영향 없음. 명시적으로 문서화 |
